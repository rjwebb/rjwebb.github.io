Task packets, an actually useful AI coding pattern

written 23rd November 2026

This concept is shamelessly stolen from How To Build Your Own Software Factory by Navan Chauhan, which is a fantastic and very long and dense article. He works for StrongDM, a company that provides a kind of authenticated and audited proxy that grants personnel and agents to secure IT infrastructure (doesn’t this sound a bit like bobnet?). I found out about this company from Commoncog, who held a Q&A in June 2026 with Navan Chauhan and Jay Taylor of StrongDM. I wasn’t there, but I listened to the recording (here, but it’s paywalled - you should subscribe to Commoncog). Simon Willison’s post from January gives some more context.

What is a task packet?

In short, a task packet is a souped-up issue template. Instead of just giving a description of the problem, proposed solution and alternatives considered, a task packet has the following sections:

  • What happens: a brief description of the current behaviour of the thing to be changed, which could be a bug (that does something other than what the user expects), or a user need that is not being met
  • Why: a description of the current relevant part of the code which is responsible for the buggy behaviour, or doesn’t currently support the feature
  • Suggested fix: a detailed description of what needs to change to fix the bug/implement the feature
  • Scope: a complete list of all the files that need to change
  • Non-goals: things that should not be done in the course of executing this task packet
  • Reproduction: what to do to reproduce the issue - i.e. a new test, which should fail at first and then pass after the change has been made
  • Validation: criteria that must be satisfied for the task to be considered done, which includes any tests that should pass, but also non-code things like specification changes
  • No-op rules: if any of these criteria are satisfied, don’t proceed with the task and alert the developer
  • Found by: the issue number and a note about how it was discovered

The above fields can be generated with Claude - a good way to do this is to write an issue by hand, then feed it to Claude (I have a command pnpm packet draft <issue number> for this), which attempts to fill in all of the fields with the information you have given, and its own reading of the codebase. If anything is unclear, contradictory or underdetermined, the agent can ask you questions which it uses to fill in the gaps. Once the task packet has been written, review it by reading it yourself. Sorry! This isn’t a totally hands-off process, yet.

Once you are happy with the task packet, you can run pnpm factory <issue number> which opens the task packet, splits it up by each section and does a few things:

  • Calls Claude Code in headless mode with a prompt constructed from all of the fields in the packet (excluding Found by) and the read/edit/write/glob/grep/todowrite and a number of pnpm and git commands as tools.
  • Checks that only files listed in “Scope” have been edited.
  • Runs the commands listed in “Validation” - this happens outside of a sandboxed environment, so it’s up to the developer to check these when reading the task packet to confirm that they are safe.

It doesn’t currently implement the “No-op rules”, beyond including them in the Claude Code prompt (i.e. there is no check blocking them).

The factory returns one of (4) output states:

  • NO_OP: if the issue can’t be worked on, e.g. if the issue is closed or it’s blocked by another issue that isn’t closed
  • ESCALATE: the task may or may not be done, but it needs a developer to check the result
  • RETRYABLE_FAILURE: the task failed for a reason unrelated to the issue itself, e.g. a clash with the name of another branch
  • PR_READY: the task was executed successfully

The reasoning behind having these terminal states is that the models in coding agents are trained to produce output - so if it can’t do something, it will try to hallucinate in order to have produced output. So you need to give models a way to give up on a task.

Does this work?

It seems to? I found that in the past, if I gave an agent an open-ended task it would save me from thinking upfront in exchange for much more thinking down the line (when the agent had implemented something I didn’t understand and it failed for a reason I didn’t understand). This is a bad habit, and in a good engineering team with human beings holding each other to account, this wouldn’t happen. So it’s important that a coding environment with a single person directing many LLMs follows the same principle. Doing the thinking up front (i.e. writing the task packet) and then getting the AI to implement it feels like the right way round to me. I know, that’s not an actual answer - I’m still just theorising as to why this is a good idea, without giving hard data or even a good empirical anecdote as a response.
